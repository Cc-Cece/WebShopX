# 优惠系统验收与测试矩阵

## 1. 验收原则

- 所有金额断言使用整数，不使用浮点近似。
- 同一个定价用例至少覆盖 SQLite 与 MySQL 业务 SQL 路径。
- 纯计算用例不访问数据库，必须可重复和属性测试。
- API 测试不仅断言应付金额，还断言选中优惠、分摊和原因码。
- 并发测试必须验证最终数据库计数、钱包流水和审计事件，而非只看 HTTP 状态。
- 退款用例必须验证“退款金额”和“返还权益”两个独立结果。

## 15. 属性测试

随机生成合法商品行和优惠规则，至少验证：

1. `baseAmount >= payableAmount >= minPayable >= 0`；
2. `baseAmount - payableAmount = totalDiscount`；
3. 每个优惠分摊和等于该优惠金额；
4. 每行优惠不超过其可减金额；
5. 调换数据库查询返回顺序不改变结果；
6. 增加一个完全不可用优惠不改变原结果；
7. 同一输入序列化/反序列化后结果相同；
8. 全额退款累计值等于实付；
9. 任意幂等操作重复 N 次，最终效果等于一次；
10. 特殊资格只扩大明确声明的槽位，不改变无关互斥规则。

## 16. 上线门槛

进入灰度前必须同时满足：

- 纯计算、事务、退款和 schema 测试全部通过；
- SQLite/MySQL 均完成并发超发测试；
- 无优惠路径与当前生产行为回归一致；
- 管理模拟器可复现全部验收示例；
- 订单价格快照可从生产式备份恢复并验证哈希；
- 紧急关闭开关经过演练；
- 特殊叠券、零元订单和补偿发券均有审计；
- 监控面板和关键告警可用；
- 灰度范围、预算上限和回滚责任人已明确。

灰度建议顺序：测试用户与测试商品 → 单服务器小人群 → 指定普通活动 → 特殊叠券 → 全量。任何金额守恒异常、重复核销或超预算都应立即停止新优惠结算，但不影响历史订单售后。
