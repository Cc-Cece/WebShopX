# 实施自由度与变更权限

## 1. 可自主决定

- 私有实现、类名、包内结构、测试夹具和小型重构；
- 不改变外部行为的性能、日志、诊断和可维护性优化；
- 将 Mxx 拆成多个提交或子 PR；
- 选择经过验证的公共库替代手写基础设施，前提是许可、体积、版本和安全可接受；
- 放弃历史原型中不合格的代码；
- 修正计划中的错误文件名或已过时事实，并留下说明。

## 2. 自主决定但必须 ADR

- Gradle 多模块/多版本工具；
- 模块边界和依赖方向细化；
- 平台端口签名、线程与生命周期模型；
- ItemEnvelope、codec、兼容域和 migration；
- Provider SPI、客户端增强、API 版本化；
- 版本族边界、产物命名、CI 矩阵生成；
- 影响多个 Mxx 的优化或改变后续执行方式的方案。

## 3. 必须由项目所有者决定

- 缩小 Fabric/Forge/NeoForge 或 Minecraft 目标范围；
- 正式版不再要求功能等价；
- 引入破坏性数据库/API/Relay/配置变化；
- 允许已知数据丢失、复制风险或不可回滚 migration；
- 将 WebShopX 客户端 Mod 设为核心功能必需；
- 修改 `main` 权限或执行任何涉及 `main` 的状态变化；
- 正式发布、标签、Release 和支持终止。

## 4. 优化判定

采用更优方案前回答：

1. 是否保持章程和验收？
2. 是否降低或清晰隔离 Paper 风险？
3. 是否能在所有目标版本族验证？
4. 是否引入难维护的反射、预处理或依赖锁定？
5. 是否有迁移和回退？
6. 新 Agent 能否仅凭 ADR 理解？

前五项中任一不能回答，不应直接实施；需要探针或所有者决定。
