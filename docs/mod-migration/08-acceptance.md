# 功能等价与质量验收

## 1. 验收原则

- “代码存在”“可编译”或“端点返回 200”不等于功能完成。
- 每项需要成功、拒绝、权限不足、重试、重复请求和故障恢复路径。
- 平台特有 UI 可不同，但同一业务必须有完整可发现路径。
- 验收证据记录命令、commit、环境、时间、结果和产物 hash。

## 2. 功能矩阵

每个平台正式版必须验证：

| 领域 | 必验业务 |
|---|---|
| 启停 | 首次启动、重启、重载、优雅停止、部分依赖失败 |
| 认证 | 玩家绑定、密码设置/重置、会话、登出、管理员登录与角色 |
| 钱包 | ShopCoin/GameCoin 查询、调整、流水、并发扣款、余额不足 |
| 支付 | 创建、查询、回调验签、重复回调、未知结果、补单 |
| 官方商城 | 商品类型、库存、购物车、结算、促销、下单、退款 |
| 市场 | 出售、收购、拍卖、竞价、补货、暂停、下架、成交记录 |
| 物品 | 在线/离线快照、完整 codec、容量、部分发货、嵌套容器 |
| 领取 | 单笔、批量、邮箱、重复领取、节点切换、不兼容域 |
| 配套 | 兑换码、会员、排行榜、通知、主题、语言、素材 |
| 管理 | 商品、订单、用户、钱包、市场、配置、审计、维护 |
| Web/API | 静态资源、鉴权、CORS、错误码、分页、上传、兼容契约 |
| Relay/集群 | 重连、租约、Redis 事件、重复/乱序消息、节点故障 |
| 命令/GUI | 命令、补全、权限、标准 GUI、无客户端增强时降级 |
| 可观测性 | 平台身份、能力、健康、结构化诊断、秘密脱敏 |

M0 必须把现有实际命令和 API 补成附录清单；缺少的现有功能不得因本表未逐名列出而豁免。

## 3. Paper 门禁

- 当前所有单元/集成测试通过；
- 所有既有目标 runtime 产物能生成且内容检查通过；
- 对同一数据库 fixture，关键 API 响应与基线兼容；
- plugin/Folia 元数据、服务依赖和资源完整；
- 真实 Paper 与 Folia 各至少一个受支持锚点完成启动和关键交易 smoke；
- 性能与线程检查不出现新增的主线程数据库/网络访问。

## 4. Mod 门禁

每个支持单元至少：

- 在干净缓存中解析依赖并可重复编译；
- JAR 含正确 Loader 元数据、入口、依赖声明、资源和许可证；
- dedicated server 安装后启动、ready、执行命令/API、持久化并重启恢复；
- 无 WebShopX 客户端附属 Mod 时核心功能完整；
- 对应 Loader 的原生物品 round-trip 和在线发货通过；
- 支持离线发货时必须验证在线/离线竞态；否则正式版不通过；
- 缺失可选 Provider 不影响无关功能；
- 与同兼容域节点共享数据库时无重复扣款/发货。

## 5. 数据与安全门禁

- 旧生产匿名快照副本完成迁移演练；
- 迁移前后行数、余额、流水、订单状态和 envelope hash 对账；
- 回滚按 [10-release-rollback.md](10-release-rollback.md) 演练；
- 恶意/超大物品、路径穿越上传、未授权 API、伪造回调和重放请求被拒绝；
- 依赖与许可证扫描没有未处置的阻塞项。

## 6. 性能预算

M0 记录现有基线；M9 固化数值。至少监测启动时间、空闲内存、API 延迟、批量发货吞吐、数据库连接、Redis 重连、物品 codec 大小/耗时和 Minecraft tick 影响。任何显著回退必须解释、修复或由所有者批准。

## 7. 完成判定

正式 Mod Release 只有在支持矩阵中所有承诺单元为 `full` 或经所有者明确接受的 `degraded`，且无 P0/P1、无未批准 P2 时才可标记 readiness。Agent 只能建议发布，不能决定进入 `main`。
