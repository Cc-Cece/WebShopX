# 项目章程与不可变约束

## 1. 成功定义

WebShopX 在同一代码库中稳定产出原插件和目标 Mod。共享业务在各平台具有相同的金额、库存、订单、权限、幂等和审计语义；平台差异通过明确适配器表达，不通过散落的加载器判断侵入业务代码。

## 2. 必须实现

- 保留现有 Paper/Purpur/Spigot/Folia 构建、命令、配置、数据、Web/API、Relay、支付和发布变体。
- Fabric、Forge、NeoForge 达到 [08-acceptance.md](08-acceptance.md) 定义的功能等价。
- 支持原版与 Mod 物品，包括注册表身份、数量、附魔、NBT/数据组件、容器内容和自定义数据。
- 支持在线与离线玩家领取、邮箱、补单、退款、市场、官方商城、钱包、支付、管理后台、审计和集群。
- 对不可安全跨平台的物品执行显式拒绝或路由，不得静默降级、替换、丢失或复制。
- 对每个正式支持单元提供可重复构建、自动测试、启动 smoke 和产物验证。

## 3. 默认方案

- 核心是服务端 Mod；Web 与标准容器式游戏内交互不得要求安装 WebShopX 客户端附属 Mod。
- 如果自定义界面或预览确需客户端代码，必须作为可选增强模块，并有无客户端时的完整功能路径。
- 业务数据库可共享，物品和领取能力按兼容域隔离。
- 外部 API 和 Relay 向后兼容；新增契约使用显式版本字段或版本化端点。

改变默认方案必须有 ADR；影响范围或产品承诺时还需项目所有者书面批准。

## 4. 不可变安全边界

- 不直接重写或删除现有 Paper 实现来“顺便支持 Mod”；先建立契约，再逐步迁移。
- 未通过 Paper 回归门禁的任务不得合并至 `mod-integration`。
- 数据库变更必须向前迁移、可备份、可验证；不得以删列、清表、重建用户数据作为常规升级方案。
- 金额使用整数最小单位；钱包变动必须经过钱包服务与流水；支付、充值、兑换、发货、领取、退款必须幂等。
- 平台 API 只能在其允许的线程和生命周期内调用。
- 未知物品格式、未知注册表或缺失 Mod 必须 fail closed，并保留原始负载以便恢复。
- 密钥、访问令牌、真实账号和环境地址不得进入仓库或测试产物。

## 5. 非目标

- 不保证不同 Minecraft 版本或不同整合包之间任意 Mod 物品可互换。
- 不承诺支持所有经济、权限、领地或物品 Mod；只承诺稳定 SPI 和支持矩阵列出的适配器。
- 不要求三个加载器共享全部平台实现代码；允许小而清晰的重复，禁止通过脆弱反射制造表面统一。
- 不在本项目内重写独立前端产品；只维护既有 Web 契约及同步构建方式。
- 不由 Agent 决定任何进入 `main` 的操作。

## 6. 允许的工程自由

程序员 Agent 可以：

- 调整内部模块、接口、包名和测试策略；
- 选择成熟的多加载器构建方式或保持显式子项目；
- 重构重复代码、改善性能、可观测性和故障恢复；
- 把任务拆成更小的提交或子 PR，只要阶段门禁不被绕过；
- 发现历史原型更优时，经验证后复用或重新实现。

但下列变化必须新增 ADR：依赖方向、平台契约、数据格式、兼容域、线程模型、版本分组、Loader 构建工具、客户端要求、外部 API、数据库迁移或发布策略。

下列变化还必须等待项目所有者决定：缩小加载器/版本/功能范围、破坏兼容、改变 `main` 权限、允许数据丢失、将客户端 Mod 设为必需、取消全功能正式版目标。

## 7. 停止条件

遇到以下情况，Agent 必须停止相关实现并记录 `blocked`，不得猜测：

- 需要项目所有者在多个会显著改变产品范围的方案中选择；
- 无法证明数据库迁移或物品转换不会造成不可恢复损失；
- 目标加载器/版本不存在可合法解析的依赖或许可冲突；
- 唯一可行方案要求直接操作 `main`；
- 当前分支包含无法安全隔离的他人修改。
